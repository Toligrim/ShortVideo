# Точечное усиление ShortVideo практиками из экосистемы Remotion

## Главный вывод

ShortVideo не нуждается ни в новом видеодвижке, ни в другом TTS-контуре, ни в универсальном «AI-видеоредакторе». Его архитектура уже сильнее большинства рассмотренных решений в самом существенном месте: слово из синтезированной речи используется не только для подсветки субтитров, а как семантический триггер геометрии, состояний и движения кадра. Дополнительные преимущества дают JSON-DSL как источник истины, дешёвая Preview-кузница, обязательный gap-скан режиссёра и критик, проверяющий реальные рендеры до полного экспорта. fileciteturn0file1

Поэтому переносить следует не готовые пайплайны, а **контракты вокруг существующей архитектуры**:

1. превратить каталог визуалов из документации «для чтения» в машиночитаемый реестр, из которого генерируются документация, тестовые сцены и подсказки режиссёру;
2. заменить фиксированные контрольные кадры на кадры, выбранные по `onWord`-событиям и состоянию анимации;
3. привязать вердикты критика к хешам JSON, word-boundary-метаданных и самих кадров;
4. добавить отдельную проверку темпа, которую невозможно выполнить по двум статичным кадрам;
5. расширить `code`-сцены переходами между семантическими состояниями кода, также управляемыми через `onWord`;
6. ввести автоматический preflight/post-render-гейт, проверяющий не «вирусность», а внутреннюю согласованность DSL, аудио и итогового файла.

Из 207 репозиториев наибольшую ценность для ShortVideo представляют не самые крупные редакторы, а более узкие проекты: `video-shotcraft` — как образец карточек визуальных механизмов, `remotion-bits` — как образец машиночитаемого реестра, `remotion-director` — как образец слепого критика и осмысленного выбора кадров, `paper-collage-video` — как образец доказуемой и аннулируемой при изменениях приёмки, `template-code-hike` — как источник семантических переходов кода, `claude-video-kit` — как источник объективного CLI-гейта. Исходный список репозиториев и их заявленные направления подтверждают, что большая часть остальных кандидатов сосредоточена на GUI, генеративных ассетах, клиппинге исходного видео, аватарах или замене TTS — то есть на областях, которые сознательно исключены требованиями ShortVideo. fileciteturn0file0

## Принцип отбора практик

Практика включалась в рекомендации, только если она удовлетворяет четырём условиям.

Во-первых, она сохраняет детерминированность: один JSON, один набор word-boundary-таймингов и одна версия компонентов должны воспроизводимо давать одинаковый кадр. Во-вторых, она усиливает именно семантику `onWord`, а не сводит слово обратно к обычному таймкоду. В-третьих, она может быть добавлена как локальный слой без замены JSON-DSL, ролей агентов, TTS-провайдеров и публикационного контура. В-четвёртых, её эффект можно проверять автоматически или через явно зафиксированные визуальные доказательства.

В результате полезные заимствования делятся на три класса.

**Контракты библиотеки** описывают, что умеет визуал, когда его следует применять, какие якоря ему нужны и где он обычно ломается. Это решает уже существующую проблему: код содержит одиннадцать story-визуалов, а агентский `catalog.md` знает только о восьми; при дальнейшем росте однострочная таблица перестанет быть достаточным носителем знаний. fileciteturn0file1

**Контракты проверки** определяют, какие именно кадры смотрит критик, к какой версии входных данных относится его вердикт и когда этот вердикт должен аннулироваться. Это особенно важно для ShortVideo: изменение TTS может оставить текст реплики прежним, но сдвинуть word boundary, а значит, изменить кадр появления пакета, узла или бейджа.

**Семантические визуальные механизмы** превращают произнесённые понятия в изменение состояния объясняемого объекта. Именно поэтому переход кода «до → после» полезнее, чем ещё один декоративный фон или набор универсальных переходов.

## Каталог визуалов как исполняемый контракт

### Машиночитаемый реестр вместо ручного `catalog.md`

В `video-shotcraft` каждый shot recipe описывается не только названием и внешним видом. В карточках фиксируются назначение, уровень энергии, рекомендуемая длительность, параметры, детали реализации и известные грабли; рядом находится рабочая TSX-реализация и визуальный preview. Репозиторий разделяет сами карточки в `references/shots/`, реализации в `demos/` и галерею, пригодную для поиска по названиям и категориям. fileciteturn2file0 fileciteturn4file0

У `av/remotion-bits` ещё полезнее не конкретные эффекты, а `registry.json`: компонент описывается через идентификатор, заголовок, назначение, тип, собственные зависимости и точные файлы реализации. Один реестр обслуживает документацию, CLI-поиск и другие способы выдачи компонентов; в нём, например, отдельно представлены детерминированная система частиц, CodeBlock с reveal/focus/highlight и утилиты staggered motion. fileciteturn17file0

Для ShortVideo стоит создать единый источник истины, например:

```text
schema/visual-registry.schema.json
video/src/visuals/registry.json
video/src/visuals/fixtures/
tools/visual_catalog.py
catalog.md                         # генерируемый файл
```

Минимальная запись визуала должна выглядеть примерно так:

```json
{
  "id": "collision-compare",
  "sceneTypes": ["story"],
  "semanticActions": [
    "compare",
    "collision",
    "same-address",
    "resolve-conflict"
  ],
  "energy": "medium",
  "implementation": "src/scenes/story/visuals/CollisionCompare.tsx",
  "paramsSchema": "#/$defs/collisionCompare",
  "anchors": {
    "required": [
      {
        "role": "collision",
        "source": "onWord",
        "description": "Момент, когда становится видно совпадение адресов"
      }
    ],
    "optional": [
      {
        "role": "resolution",
        "source": "onWord"
      }
    ]
  },
  "timing": {
    "settleFrames": 10,
    "minimumReadableHoldFrames": 18
  },
  "knownPitfalls": [
    "Два ключа не должны визуально попадать в разные адреса",
    "Финальное состояние не должно возникать до слова-якоря"
  ],
  "fixtures": [
    "fixtures/collision-compare/basic.json",
    "fixtures/collision-compare/long-labels.json"
  ]
}
```

Ключевое отличие от обычного каталога motion-компонентов — поля `semanticActions` и `anchors`. Режиссёр должен искать не «красивую карточку», а механизм, подходящий к действию реплики: сравнить, распространить, вытеснить, освободить память, развернуть стек, вернуть значение. Поле `anchors.required` позволяет валидатору до TTS проверить, что JSON содержит соответствующие роли, а после TTS — что каждое слово разрешилось в единственный word boundary.

### Генерация документации и тестов из реестра

`catalog.md` следует сделать артефактом сборки, а не редактируемым источником. Команда:

```bash
python3 tools/visual_catalog.py generate
python3 tools/visual_catalog.py check
```

должна:

- сгенерировать таблицу для агентов;
- проверить, что каждый вариант из TypeScript union зарегистрирован;
- проверить, что каждый зарегистрированный визуал поддержан JSON Schema;
- проверить существование файла реализации и всех fixture-файлов;
- проверить, что в Preview-композиции можно отрендерить хотя бы один кадр каждого fixture;
- завершаться ошибкой, если сгенерированный `catalog.md` отличается от закоммиченного.

Это напрямую закрывает обнаруженное расхождение с `recursion-call`, `stack-grow` и `stack-compare`: после такой проверки новый visual нельзя будет добавить только в TypeScript и эпизод, забыв агентскую документацию. fileciteturn0file1

### Поиск для gap-скана режиссёра

Из `remotion-bits` стоит перенять идею поиска по каталогу, но не обязательно его CLI или MCP целиком. Достаточна локальная команда:

```bash
python3 tools/visual_catalog.py find \
  --action compare \
  --action collision \
  --scene story \
  --max-results 5
```

Она должна возвращать режиссёру не только имена, но и:

```text
collision-compare
Соответствие: 0.92
Действия: compare, collision, same-address
Нужные якоря: collision
Энергия: medium
Грабли: не показывать разные конечные адреса
Fixture: fixtures/collision-compare/basic.json
```

Тогда обязательный gap-скан перестанет зависеть от того, вспомнил ли агент нужную строку в Markdown. Более того, его оценка `1–5` сможет опираться на явно сопоставленные `semanticActions`, а продюсер сможет проверить, какие результаты поиска видел режиссёр.

### Что брать из `video-shotcraft`, а что не брать

Перенять следует **формат recipe card, preview-fixture и known pitfalls**, но не готовый визуальный язык продуктовых промороликов. Большая часть карточек `video-shotcraft` посвящена демонстрации интерфейсов, брендингу, 2.5D-камерам и рекламной динамике; это полезная библиотека движений, но не готовая стилистическая система для русскоязычных уроков информатики. fileciteturn2file0

Практический принцип: из каждой внешней карточки брать только переносимый глагол движения. Например:

| Внешний паттерн | Что можно перенести | Что не переносить |
|---|---|---|
| `title-demote-to-label` | заголовок уменьшается и становится постоянной меткой состояния | рекламную типографику и палитру |
| `list-stack-press` | физическое сжатие стека при добавлении элемента | декоративную карточную стилизацию |
| `timeline-travel` | движение вдоль последовательности состояний | общую композицию продуктового ролика |
| `typewriter-moves` | ошибка → удаление → исправленный ввод | фиксированные тайминги и брендинг |
| `chart-live-moves` | перестройка элементов при изменении данных | декоративные частицы без учебной функции |

## Критик, привязанный к семантическим событиям

### Отказ от фиксированных кадров в пользу review-плана

Текущий критик снимает по два кадра на сцену примерно на 35% и 75% её длительности. Это дешёво, но не гарантирует попадания в смысловой момент: короткая коллизия может произойти на 52%, пакет может ещё лететь на 35%, а финальное состояние стека — появиться после 75%. fileciteturn0file1

`Zane-0x5a/remotion-director` описывает важное наблюдение: равномерно выбранные still-кадры часто замораживают нормальную анимацию в неудачной промежуточной фазе. Критик тогда воспринимает временное наложение или движение текста как дефект статической композиции. В проекте поэтому выбираются прежде всего кадры устойчивых пауз, а промежуточные кадры явно помечаются как движение, которое нельзя оценивать по правилам settled layout. fileciteturn7file0

В ShortVideo этот механизм можно реализовать точнее, чем через анализ пикселей: необходимые события уже заданы `onWord`.

Для каждой сцены следует генерировать `review-plan.json`:

```json
{
  "sceneId": "hash-collision",
  "inputFingerprint": "sha256:...",
  "frames": [
    {
      "frame": 82,
      "kind": "settled",
      "reason": "После якоря collision и settleFrames=10",
      "anchor": "коллизия",
      "judge": ["semantic-fit", "layout", "readability"]
    },
    {
      "frame": 109,
      "kind": "motion",
      "reason": "Пакет находится на траектории",
      "anchor": "пакет",
      "judge": ["trajectory", "occlusion"],
      "doNotJudge": ["final-layout"]
    },
    {
      "frame": 146,
      "kind": "final",
      "reason": "Последнее устойчивое состояние до выхода",
      "judge": ["semantic-result", "readability", "safe-zones"]
    }
  ]
}
```

Алгоритм выбора:

1. Собрать все `onWord`-события сцены и перевести их в кадры через существующий `wordFrame()`.
2. Для каждого события добавить кадр `eventFrame + settleFrames`, где `settleFrames` берётся из recipe card визуала.
3. Добавить кадр середины самого длинного устойчивого интервала между событиями.
4. Добавить последний устойчивый кадр до перехода сцены.
5. Для траекторий, перестроений и морфов добавить один кадр с `kind: motion`, но запретить критику считать промежуточное расположение финальным layout-дефектом.
6. Ограничить бюджет, например, тремя кадрами для простой сцены и пятью для сцены с несколькими семантическими событиями.

Таким образом, число контрольных кадров увеличивается только там, где сцена действительно сложна. Для hook или title-slam может остаться два кадра; для hash collision или garbage collection понадобится четыре.

### Контекстный «файрвол» для критика

В `remotion-director` критик намеренно не получает дизайн-документ, исходный код и объяснение автора. Он видит реальные кадры и краткий исходный brief; иначе модель склонна подтверждать намерение дизайнера вместо оценки фактического пиксельного результата. Автор и критик не общаются напрямую: оркестратор передаёт наблюдения, не раскрывая критическому агенту внутреннюю рационализацию решения. fileciteturn7file0

Для ShortVideo не следует делать критика полностью «слепым» к семантике: он должен понимать, что именно объясняется. Но его вход нужно сократить до:

```text
Цель сцены:
«Показать, что два разных ключа получили один индекс таблицы».

Реплика:
«Это называется коллизией: два ключа получили один адрес».

Событие кадра:
После слова «коллизией», устойчивое состояние.

Оцени:
семантическую точность, читаемость, перекрытия, safe-зоны,
наличие однозначного визуального причинно-следственного отношения.
```

Не следует передавать:

- отчёт режиссёра о том, почему он выбрал визуал;
- gap-оценку;
- описание ожидаемого художественного эффекта;
- сообщения «здесь специально сделано…»;
- список уже выполненных исправлений до того, как критик сам посмотрел кадр.

В двух разрешённых раундах лучше сохранять одного и того же критика или, как минимум, передавать ему прежний список собственных дефектов и новые кадры. В `remotion-director` отмечено, что полностью новый критик в каждом раунде склонен каждый раз изобретать новый набор замечаний и мешает сходимости; постоянный критик поддерживает стабильный порог качества. fileciteturn7file0

### Отдельный аудит темпа

Статичный кадр не показывает, находилась ли надпись на экране 0,4 секунды или 3 секунды. `remotion-director` поэтому отделяет финальный tempo pass от эстетического критика: после визуальной сходимости свежий агент анализирует фактические длительности вступления, удержания и выхода элементов. fileciteturn7file0

Для ShortVideo tempo-аудитор должен получать не видеоописание, а вычисленный event schedule:

```text
Сцена hash-collision, 168 кадров

0–31       ввод узлов
32         onWord «ключ»
32–78      ключ A видим 1.53 с
79         onWord «второй»
79–111     одновременно видны A и B 1.07 с
112        onWord «коллизия»
122        состояние settled
122–167    результат читаем 1.53 с
```

Проверки должны быть специфичными для архитектуры:

- достаточно ли времени между появлением термина и сменой сцены;
- успевает ли зритель увидеть результат действия после ключевого слова;
- не происходят ли три независимых события на соседних словах;
- не появляется ли объясняющий бейдж до того, как произнесена причина;
- не исчезает ли визуал сразу после завершения spring-анимации;
- остаётся ли финальное состояние хотя бы заданное число кадров;
- не конкурирует ли karaoke-подсветка с главным изменением геометрии.

Tempo-аудитор не должен переписывать сценарий или выбирать новый visual. Его допустимые изменения: `settleFrames`, локальная задержка относительно word anchor, tail сцены, stagger и длительность перехода. При этом абсолютный источник времени остаётся прежним: TTS и `onWord`.

### Хеш-привязка доказательств и вердиктов

`paper-collage-video` реализует более строгий подход к приёмке: quality report связывает проверяемые цели, evidence-файлы и их SHA-256; изменение файла, семантического контракта или доказательства аннулирует прежний review. Проект генерирует review scaffold и contact sheet, а запись результатов отклоняется целиком, если входные данные успели измениться. fileciteturn6file0

ShortVideo уже применяет похожее мышление в публикации: review-assets неизменяемы и связаны с конкретным видео и метаданными. Поэтому тот же паттерн логично перенести на внутреннего критика. fileciteturn0file1

Для каждой сцены fingerprint должен включать:

```text
SHA-256:
- canonical JSON конкретной сцены;
- narration;
- соответствующего фрагмента meta.json с word boundaries;
- версии schema;
- файлов компонентов, реально участвующих в рендере;
- используемых шрифтов/Lottie/SFX-ассетов;
- review-plan.json;
- каждого PNG-доказательства.
```

`critic-report.json`:

```json
{
  "episode": "hash-tables",
  "sceneId": "hash-collision",
  "evidenceFingerprint": "sha256:abc...",
  "reviewer": "critic",
  "verdict": "accepted",
  "checkedFrames": [
    {
      "file": "frame-collision-settled.png",
      "sha256": "..."
    }
  ],
  "checks": {
    "semanticFit": "pass",
    "readability": "pass",
    "safeZones": "pass",
    "occlusion": "pass"
  }
}
```

Особенно важно включить `meta.json`. Если голос произнёс слово на другом кадре, прежний PNG и прежний вердикт больше не доказывают корректность новой версии, даже если `episodes/<slug>.json` не изменился.

При этом не обязательно аннулировать весь эпизод. Можно вычислять fingerprint отдельно по сценам и повторно проверять только те сцены, на которые повлияло изменение narration, word boundaries или компонента.

## Семантические визуальные механизмы и автоматические гейты

### Переходы между состояниями кода из `template-code-hike`

Текущий `CodePanel.tsx` использует Prism для подсветки синтаксиса, что хорошо решает статическое отображение, но не объясняет изменение программы как процесс. fileciteturn0file1

В официальном `remotion-dev/template-code-hike` файл `src/CodeTransition.tsx` сохраняет DOM-снимок старого состояния токенов, вычисляет переходы к новому состоянию через `getStartingSnapshot()` и `calculateTransitions()`, а затем интерполирует изменения каждого токена по кадрам. Там же предусмотрены annotation handlers для inline-токенов, callout и ошибок. fileciteturn15file0

`src/annotations/Callout.tsx` показывает отдельный паттерн: inline-аннотация превращается в привязанную к строке выноску, способную показывать текст или дополнительный code block. fileciteturn16file0

Для ShortVideo это следует оформить как расширение существующего типа `code`, а не новый верхнеуровневый движок:

```json
{
  "type": "code",
  "language": "python",
  "narration": "Сначала функция вызывает саму себя. Затем добавляем базовый случай.",
  "states": [
    {
      "id": "recursive-only",
      "onWord": "вызывает",
      "code": "def fact(n):\n    return n * fact(n - 1)",
      "annotations": [
        {
          "type": "focus",
          "line": 2
        }
      ]
    },
    {
      "id": "with-base-case",
      "onWord": "базовый",
      "code": "def fact(n):\n    if n <= 1:\n        return 1\n    return n * fact(n - 1)",
      "annotations": [
        {
          "type": "callout",
          "line": 2,
          "text": "Условие остановки"
        }
      ]
    }
  ]
}
```

Применимость именно к ShortVideo заключается в том, что переход токенов можно запускать не через `frame: 30`, как в типовом demo, а через:

```ts
const startFrame = wordFrame(words, state.onWord);
const localFrame = frame - startFrame;
```

Это даёт несколько педагогически сильных визуалов:

- добавление base case в рекурсию;
- превращение линейного поиска в обращение по индексу;
- исправление off-by-one;
- появление условия цикла;
- изменение значения переменной с синхронным обновлением вывода;
- подсветка строки, породившей исключение;
- удаление ссылки и последующая работа сборщика мусора.

Копировать реализацию буквально не стоит. Например, `Callout.tsx` из шаблона использует фиксированный диапазон кадров появления; в ShortVideo этот диапазон должен начинаться от word anchor. fileciteturn16file0

Рекомендуемый порядок внедрения:

1. Добавить `states[]` и `annotations[]` в schema.
2. Поддержать только два состояния и `focus/callout`.
3. Создать один fixture для рекурсии и один для ошибки.
4. Добавить проверку уникальности `onWord`.
5. На втором этапе разрешить три-четыре состояния и token-level morph.
6. Не заменять текущий Prism-компонент для простых статических сцен: новый механизм должен применяться только там, где изменение кода является самим объясняемым событием.

### Объективный verifier из `claude-video-kit`

В `runesleo/claude-video-kit` файл `scripts/verify-shorts.mjs` запускается как CLI-гейт, использует `ffprobe` и `ffmpeg`, проверяет размер холста, длительность, интервалы между сценами и активность hook. Он умеет получать границы сцен не только из анализа пикселей, но и из render metadata, сверяя рассчитанную длительность расписания с фактической длительностью файла. Ошибка hard gate приводит к ненулевому exit code. fileciteturn10file0

Из него следует перенять **структуру проверяющей команды**, но не конкретные пороги. Ограничение в 60 секунд противоречит заявленным 55–70 секундам ShortVideo, а правило «смена сцены каждые три секунды» может ухудшить учебное объяснение. fileciteturn0file1

Предлагаемый verifier:

```bash
python3 tools/verify_episode.py \
  episodes/hash-tables.json \
  --meta out/hash-tables/meta.json \
  --video out/hash-tables.mp4
```

Гейт следует разделить на три уровня.

#### Проверки до TTS

Жёсткие ошибки:

- visual существует в реестре;
- параметры соответствуют schema;
- каждый обязательный anchor role присутствует;
- `onWord` содержится в narration после нормализации регистра и пунктуации;
- неоднозначное повторение слова либо запрещено, либо уточнено полем `occurrence`;
- story visual зарегистрирован и имеет fixture;
- каталог сгенерирован из актуального реестра.

#### Проверки после TTS

Жёсткие ошибки:

- каждый `onWord` разрешился ровно в один word boundary;
- порядок событий соответствует порядку слов;
- event frame находится внутри сцены;
- settled frame не выходит за пределы сцены;
- voice duration совпадает с рассчитанным scene timeline;
- ни один обязательный визуальный результат не оказывается полностью внутри transition-out.

Предупреждения:

- два независимых события разделены менее чем, например, шестью кадрами;
- финальное состояние держится менее заданного recipe card минимума;
- в сцене есть длинный период без смысловых изменений;
- на одном слове запускается слишком много конкурирующих анимаций;
- semantic event совпадает с сильной сменой karaoke-строки или межсценовым переходом.

#### Проверки итогового MP4

Жёсткие ошибки:

- фактические ширина, высота, fps и длительность не соответствуют composition metadata;
- декодированный frame count отличается от ожидаемого больше допуска;
- отсутствует или обрезан аудиопоток;
- файл не читается `ffprobe`;
- первая или последняя сцена короче вычисленного расписания;
- публикационный review связан не с этим хешем MP4.

Предупреждения:

- размер файла выше эксплуатационного лимита;
- peak audio или loudness вышли за локально выбранный диапазон;
- обнаружен полностью одинаковый участок кадров необычной длительности;
- итоговые субтитры пересекают safe-zone по автоматически рассчитанным bounding boxes.

Такой verifier полезнее попытки заставить критика визуально замечать ошибки, которые можно доказать числами.

### Отдельный контактный лист субтитров

В `paper-collage-video` subtitle review отделён от composition proof: проверяется контактный лист субтитров из закодированного результата, поскольку корректный React/CSS не гарантирует корректность итогового видеокодирования и отображения глифов. fileciteturn6file0

Для русского языка это особенно практично: один лист может включать кадр каждого переноса karaoke-строки, слова с длинными терминами, кириллицу рядом с латиницей, подчёркивания, пути, код и знаки пунктуации. Контактный лист следует включить в evidence fingerprint критика, но вынести в отдельную категорию `subtitle-typography`, чтобы дефект karaoke не аннулировал проверку семантики диаграммы и наоборот.

### Осмысленная судьба `noise`, `paths` и `shapes`

Три официальных пакета уже находятся в `package.json`, но фактически не используются; при этом дуги пакетов и некоторые эффекты реализованы вручную. fileciteturn0file1

Не стоит объявлять их внедрение самостоятельной целью. Правильное решение — короткий технический RFC для каждого:

| Пакет | Проверяемая гипотеза | Решение |
|---|---|---|
| `@remotion/paths` | уменьшает ли он сложность траекторий и позволяет ли единообразно получать позицию, касательную и ориентацию объекта | внедрить только через общий `PathMotion`, если тесты показывают выигрыш |
| `@remotion/shapes` | дают ли примитивы реальную повторно используемую семантику для diagram/story | оставить только при наличии двух и более визуалов-потребителей |
| `@remotion/noise` | нужен ли детерминированный дрейф для объясняющего объекта, а не декоративного фона | удалить, если нет конкретного учебного применения |

Публичный JSON-контракт при такой миграции меняться не должен. Например, `packet.arc` может остаться прежним, а внутренняя реализация траектории — перейти на общий path adapter. Если пакет не даёт измеримого упрощения, его лучше удалить, чем сохранять как «будущий roadmap».

## Что следует сознательно пропустить

### GUI-редакторы и таймлайны

`openvideodev/react-video-editor`, `OpenChatCut`, `clip-js`, `editor-pro-max`, `hyperedit`, `SceneDirector` и другие проекты из списка строят визуальный редактор, многодорожечный timeline или интерактивное редактирование путей. fileciteturn0file0

Для ShortVideo это не точечное усиление, а создание второго источника истины. Появятся два представления одного ролика — JSON-DSL и timeline state — и потребуется двусторонняя синхронизация `onWord`, параметров визуала, аудиометаданных и ручных правок.

Допустимо заимствовать оттуда только небольшие диагностические инструменты, например overlay траектории или рамку safe-zone в Preview. Сохранять путь из GUI обратно в JSON не следует, пока нет конкретного визуала, который невозможно удобно параметризовать декларативно.

### Генеративные видео, изображения, аватары и stock-B-roll

Репозитории, построенные вокруг Veo, Seedance, FLUX, image generation, avatars, lip-sync, стоковых изображений или автоматического B-roll, противоречат принципу проекта. Их asset engines, model routers и cost gates не дают преимущества детерминированной код-анимации. В рассматриваемом списке к этой группе относятся, среди прочего, `super-video-maker-skill`, `vanta`, `remotion-superpowers`, `ai-cinema-studio-engine`, `vox-video-starter` и многочисленные faceless-video-конвейеры. fileciteturn0file0

Даже если в таких проектах есть полезный Remotion-компонент, его следует оценивать отдельно от генеративной части и переносить только как чистую TSX-механику с локальным fixture.

### Новые TTS и voice cloning

`video-podcast-maker`, `elevenlabs-remotion-skill`, VOICEVOX-шаблоны, MiniMax/IndexTTS/voice-cloning-проекты решают другую задачу. У ShortVideo уже есть Edge TTS и Gemini fallback, а word-boundary-массив является частью управляющего API сцены. fileciteturn0file0 fileciteturn0file1

Замена голоса здесь несёт необычно высокий архитектурный риск: важно не только качество аудио, но и стабильность границ слов, нормализация русского текста, повторяемость `onWord` и возможность бесплатно синтезировать сцену заново. Поэтому из внешних TTS-проектов не следует переносить ни провайдеры, ни voice profiles. Допустимы только нейтральные механизмы: словари произношения, нормализация чисел и технических терминов, если они не нарушают word-boundary-контракт.

### Чужие JSON-композиторы

`vidosy`, `remotion-scene-composer` и похожие config-driven проекты декларативно собирают сцены, переходы, аудио и текст. fileciteturn0file0

Их DSL не нужно интегрировать: ShortVideo уже имеет более содержательную модель, где слово управляет сценой, а schema связана с агентным gap-сканом и каталогом визуалов. Попытка сделать «универсальный» DSL почти наверняка ослабит типизацию семантических действий до примитивов `text/image/transition`.

Из таких проектов можно брать отдельные идеи валидации или layout, но не типы верхнего уровня и не формат проекта.

### Полный импорт библиотек компонентов

`remotion-bits`, `Remocn`, `remotion-scenes`, `remotion-templates` и другие библиотеки полезны как карьеры механизмов, но их не следует подключать оптом. Машиночитаемый registry `remotion-bits` показывает, что даже один компонент может тянуть набор собственных utilities и зависимостей. fileciteturn17file0

Предпочтительный процесс:

1. выбрать конкретный механизм;
2. изучить его лицензию и зависимости;
3. перенести минимальный код в собственный visual primitive;
4. адаптировать timing к `onWord`;
5. добавить собственный fixture;
6. привести типографику, цвета и easing к языку ShortVideo;
7. записать источник и изменения в recipe card.

Так сохраняется единый визуальный язык и уменьшается риск, что каждый эпизод станет выглядеть как набор несвязанных demo-компонентов.

### Множественные независимые «дубли» ролика

`remotion-director` делает несколько независимых draws и слепо выбирает наиболее перспективный перед critic loop. Это оправдано для коротких художественных motion pieces, где цель — найти редкую сильную концепцию. fileciteturn7file0

Для ShortVideo полное копирование этого паттерна слишком дорого: сценарий, `onWord`, TTS и библиотечный рост уже формируют сложный производственный контракт. Генерация трёх полных реализаций одной сцены увеличит код, TTS-запуски и нагрузку на критика.

Можно использовать облегчённый вариант только в кузнице: если gap-скан требует нового visual, режиссёр создаёт не три полноценные реализации, а три дешёвых статических или упрощённых Preview-варианта одного ключевого состояния. После выбора реализуется только победитель.

### Бесконечный critic loop

`remotion-director` запускает цикл до сходимости, тогда как ShortVideo ограничивает его двумя кругами. fileciteturn7file0 fileciteturn0file1

Ограничение ShortVideo следует сохранить. Для регулярного образовательного конвейера предсказуемая стоимость важнее попытки автономно довести каждую сцену до художественного максимума. Перенять стоит слепоту критика, осмысленную выборку кадров и стабильность его памяти, но не неограниченное число итераций.

### Matrix-rendering в GitHub Actions на текущем этапе

`Remotion-Matrix-Renderer` делит диапазон кадров между GitHub Actions workers, отдельно рендерит аудио, создаёт muted MP4-фрагменты и затем объединяет их через FFmpeg. В опубликованном примере для 9000 кадров десять workers заметно сокращают время по сравнению с одним, но результат зависит от доступности runner-ов и расходует Actions minutes. fileciteturn11file0 fileciteturn12file0

Для обычных роликов 55–70 секунд это пока преждевременная сложность. Workflow также требует аккуратно гарантировать одинаковое окружение шрифтов, Chromium, ассетов, dependency cache и кодеков во всех workers. Отдельный рендер аудио и склейка сегментов создают дополнительную поверхность ошибок, хотя ShortVideo уже синхронизирует сцены по аудио.

Сначала следует добавить обычный GitHub Actions-гейт:

```text
schema validation
TypeScript check
registry parity check
Preview fixture stills
одна короткая smoke-композиция
```

К распределённому рендеру стоит вернуться, только если longform-эпизоды регулярно превышают приемлемое время. И даже тогда для архитектуры ShortVideo логичнее рассмотреть шардирование по целым сценам с последующей склейкой, а не произвольные frame ranges: сцена уже является естественной единицей аудио, JSON, word boundaries и review fingerprint.

### «Вирусные» пороги из чужих verifier-ов

Порог «не более трёх секунд на сцену» и обязательная смена в первые две секунды из `verify-shorts.mjs` нельзя принимать как универсальную норму. Эти значения отражают конкретную редакционную модель другого проекта. fileciteturn10file0

ShortVideo должен измерять не частоту cuts, а частоту **семантических событий**. Одна diagram-сцена может длиться восемь секунд, но за это время на словах последовательно появятся узел, пакет, канал и результат. Визуальный scene detector назовёт её статичной или одной сценой, хотя объяснение динамично. Поэтому verifier должен читать schedule из DSL и `meta.json`.

## План внедрения

### Фундамент библиотеки

Сначала следует исправить существующий drift каталога и создать registry.

Изменения:

```text
schema/visual-registry.schema.json
video/src/visuals/registry.json
video/src/visuals/fixtures/*.json
tools/visual_catalog.py
tests/test_visual_registry.py
```

Критерии готовности:

- все одиннадцать текущих story-визуалов зарегистрированы;
- `catalog.md` полностью генерируется;
- CI ловит отсутствующую регистрацию;
- у каждого визуала есть хотя бы один Preview-fixture;
- режиссёр умеет делать `find` по semantic action;
- обязательный отчёт режиссёра указывает ID recipe card, а не свободное имя.

На этом же этапе следует добавить поля `knownPitfalls`, `settleFrames`, `minimumReadableHoldFrames` и `anchor roles`. Они понадобятся следующему этапу.

### Review-план и новый протокол критика

Затем реализуется выбор evidence-кадров.

Изменения:

```text
tools/build_review_plan.py
tools/render_review_stills.py
out/<slug>/review/review-plan.json
out/<slug>/review/contact-sheet.png
```

Критерии готовности:

- кадры выбираются по `onWord`, final state и устойчивому hold;
- motion-кадры маркируются отдельно;
- количество кадров зависит от сложности сцены;
- критик не получает rationale режиссёра;
- второй круг сравнивает те же review targets;
- producer сохраняет verbatim-замечания критика.

Текущие 35% и 75% можно оставить как fallback для сцен без событий, но не как основной алгоритм.

### Доказуемая приёмка и tempo-аудит

После стабилизации review-plan добавляются fingerprints:

```text
tools/review_fingerprint.py
schema/critic-report.schema.json
out/<slug>/review/critic-report.json
out/<slug>/review/tempo-report.json
```

Критерии готовности:

- изменение word boundaries аннулирует соответствующую сцену;
- изменение unrelated сцены не аннулирует весь эпизод;
- вердикт нельзя записать для устаревшего contact sheet;
- tempo-аудитор видит event schedule, но не меняет содержание сцены;
- producer проверяет актуальность fingerprint перед полным render.

Здесь разумно переиспользовать модели immutable review-assets и hashing-подходы уже существующего publishing-модуля, а не создавать второй несовместимый формат. fileciteturn0file1

### Автоматический verifier

Verifier можно внедрять параллельно с fingerprint-слоем.

Минимальная версия должна проверять:

```text
разрешение onWord
frame bounds
соответствие длительности аудио и timeline
ожидаемый размер/fps/dлительность MP4
наличие audio stream
минимальный final hold
актуальность review fingerprint
```

Её следует запускать:

```text
после validate.py
после TTS
после полного render
перед созданием Telegram review-card
```

Это дешёвое усиление, потому что большинство данных уже существует.

### Семантические состояния кода

После укрепления каталога и приёмки стоит добавить `code.states[]`.

Первый вертикальный slice:

- один Python-пример;
- два состояния;
- один `focus`;
- один `callout`;
- переход начинается от `onWord`;
- fixture рендерится в кузнице без TTS;
- critic review-plan включает состояние до перехода, motion-кадр и settled-результат.

Только после этого следует решать, подключать Code Hike как зависимость или переносить минимальный механизм token snapshots в собственный компонент. Сам паттерн из `CodeTransition.tsx` ценен; зависимость не является обязательной частью рекомендации. fileciteturn15file0
