# publisher-approve-ack — кнопка Approve/Reject в Telegram ничего не делает

Не привязано к одному эпизоду (баг в самом сервисе одобрения публикаций,
`tools/publishing/telegram.py`) — задокументировано отдельной папкой, а не
внутри `corrections/<slug>/`, потому что это дефект инфраструктуры, а не
контента конкретного ролика; затронутая заявка на момент инцидента —
`auto-20260831-050001`.

## Правка 1 (2026-08-31)

### Что сломалось
Пользователь нажал «✅ Approve» на карточке ревью в Telegram — ничего не
произошло: заявка осталась висеть `review_pending`, никакого видимого
эффекта (ни смены карточки, ни ошибки на экране пользователя). Дословно от
пользователя: «У меня почему-то опять кнопка approve ничего не отправляет».

### Как нашли
Пользователь сообщил о проблеме напрямую (не автоматика). Диагностика:
`journalctl --user -u shortvideo-publisher-bot.service` показал:
```
Aug 31 10:51:44 … Telegram callback processing failed for update 722130739:
  Telegram API: Bad Request: query is too old and response timeout expired or query ID is invalid
Aug 31 11:04:13 … Telegram callback processing failed for update 722130740:
  Telegram API: Bad Request: query is too old and response timeout expired or query ID is invalid
```
— то есть ДВЕ попытки нажатия (или ретрая Telegram) закончились одинаково.
Между этими строками и вокруг них — множество `не удалось подключиться к
Telegram: [SSL: UNEXPECTED_EOF_WHILE_READING]` / `[Errno 101] Network is
unreachable` за период ~09:14–11:28 MSK. `sqlite3 …/publisher.sqlite3
"select … from publications"` подтвердил: `state=review_pending`,
`approved_at` пусто, токен approve-действия в `telegram_actions` не
`consumed_at`.

### Почему сломалось (root cause)
Два независимых слоя, оба нужны для полной картины:

**1. Сетевой (внешний, ожидаемый) слой.** Хост `shuvalova` периодически теряет
и восстанавливает маршрут к VPN (см. `~/.claude/CLAUDE.md`: `wlan0` флапает,
`vless-direct-routes.timer` перевыставляет прямые маршруты каждые 2 мин,
DHCP-рефреш/networkd resync их смывает). Это самовосстанавливающийся,
задокументированный и ожидаемый фон, не то, что нужно чинить руками. Пока
маршрут лежал, `getUpdates` long-polling бота (`tools/telegram_bot.py`)
не мог достучаться до Telegram и копил бэклог обновлений.

**2. Код (внутренний, реальный баг).** Когда бот наконец разобрал бэклог,
Telegram уже считал конкретный `callback_query` устаревшим и отверг
`answerCallbackQuery` ошибкой «query is too old…» — это нормальная реакция
Telegram API на поздний ack, НЕ признак того, что сама сеть всё ещё плоха
(ответ вообще-то пришёл, просто с отказом). Баг был в
`tools/publishing/telegram.py::_process_callback` (строки вокруг
`self.api.answer_callback_query(...)`, до правки): этот вызов стоял ПЕРЕД
`self.store.apply_telegram_action(...)` — тем самым единственным местом,
которое реально меняет состояние публикации, — без `try/except`. Когда ack
падал с `TelegramError`, исключение улетало из `_process_callback` наружу,
и `apply_telegram_action` не вызывался вовсе: нажатие технически дошло до
бота (Telegram его доставил), но его обработка обрывалась раньше, чем до
записи в БД. Внешний `poll_once` (`tools/publishing/telegram.py`) ловит
такие исключения и **всё равно продвигает курсор** — сознательное решение
(«a single update must not wedge the cursor forever»), чтобы одно плохое
обновление не блокировало всю очередь навсегда. Побочный эффект: тот же
самый апдейт никогда не будет предложен боту повторно — нажатие терялось
безвозвратно, без единого сообщения об ошибке на стороне пользователя в
Telegram (просто «ничего не произошло»).

Важное наблюдение: `apply_telegram_action` — чистая локальная транзакция
SQLite, сети не касается вообще. То есть именно в момент отказа ack
(«query is too old» — код 400 от Telegram, не сетевой таймаут) сеть на
самом деле УЖЕ была рабочей — просто конкретный колбэк успел протухнуть,
пока бэклог полз. Иными словами: реальная запись в БД в обоих
зафиксированных случаях, скорее всего, прошла бы успешно, если бы её вообще
попытались сделать.

### Что исправили в ролике
Не применимо — баг инфраструктурный, не привязан к контенту конкретного
эпизода. Публикация `cd29341224cc4083acac8696a56b6a67` (эпизод
`auto-20260831-050001`) на момент правки так и осталась `review_pending`;
пользователю нужно нажать Approve ещё раз после перезапуска бота (токен
кнопки не израсходован, второе нажатие сгенерирует новый `callback_query`
с тем же токеном действия).

### Что исправили в конвейере
`tools/publishing/telegram.py::_process_callback` — вызов
`self.api.answer_callback_query(...)` обёрнут в `try/except TelegramError`:
неудачный ack теперь только логируется, `self.store.apply_telegram_action(...)`
выполняется в любом случае. Дизайн «ответить быстро, чтобы у Telegram погас
спиннер» сохранён как оптимизация счастливого пути, но перестал быть точкой
отказа для самого главного — фактической записи в БД.

`tools/test_publishing_telegram.py` — новый регресс-тест
`test_stale_ack_does_not_drop_the_approve_action`: поднимает
`FakeTelegramApi`-подобный дублёр, у которого `answer_callback_query` всегда
бросает `TelegramError` с ТЕМ ЖЕ текстом, что был в продакшн-логе, гоняет
`poll_once` с одним approve-колбэком и проверяет, что публикация всё равно
переходит в `APPROVED`, а в outbox появляется `target.publish`. Проверено
руками (`git stash` на файл фикса): без правки тест падает с
`AssertionError: REVIEW_PENDING != APPROVED` — воспроизводит ровно
зафиксированный дефект, не «зелёный по построению».

`shortvideo-publisher-bot.service` перезапущен (`systemctl --user restart`),
чтобы боевой процесс подхватил фикс без ожидания следующего деплоя.

Коммит (ветка `feature/telegram-social-publishing`):
`ffbc5a1` — fix: не терять approve/reject при упавшем answerCallbackQuery

### Урок / класс ошибки
- **Класс — «ack ≠ факт»**: любое место в конвейере, где сначала
  подтверждается получение внешнему сервису (Telegram, любому API с
  колбэками/вебхуками), а ПОТОМ выполняется реальная работа — рискует
  потерять работу целиком, если подтверждение не удалось, хотя сама работа
  прекрасно выполнима независимо. Общее правило на будущее для этого
  кодовой базы: подтверждение внешнему сервису — best-effort и никогда не
  должно быть на критическом пути к durable-состоянию; при ревью новых
  интеграций с колбэками проверять именно этот порядок.
- Сетевые SSL/route-флапы хоста `shuvalova` — фон, уже задокументирован в
  `~/.claude/CLAUDE.md`, сам себя чинит таймером; не нужно "чинить" сеть
  каждый раз, когда всплывает такой инцидент — искать баг в коде, который
  не выдерживает временную недоступность сети, а не бороться с самой
  недоступностью.
- При следующих похожих жалобах «кнопка ничего не делает» — первым делом
  смотреть `journalctl --user -u shortvideo-publisher-bot.service` на
  `Telegram callback processing failed for update …`, затем состояние
  публикации и `telegram_actions.consumed_at` в
  `~/.local/share/shortvideo/publisher/publisher.sqlite3` (не забыть — это
  боевой путь, не `var/publisher/` внутри репозитория, см.
  `corrections/auto-20260831-050001/REPORT.md`).
