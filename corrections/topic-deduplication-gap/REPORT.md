# topic-deduplication-gap — автопродюсер трижды выпустил одну и ту же тему QR-кода

Не привязано к одному эпизоду (баг в самом промпте/логике планировщика,
`tools/producer_scheduler.py`) — задокументировано отдельной папкой, а не
внутри `corrections/<slug>/`, по правилу из `corrections/CLAUDE.md` для
инфраструктурных дефектов. Затронуты три эпизода:
`auto-20260820-193301`, `auto-20260830-082101`, `auto-20260831-114201`→
на самом деле третий — `auto-20260831-150301` (см. ниже, слайд правки).

## Правка 1 (2026-08-31)

### Что сломалось

Пользователь заметил, что тема «почему QR-код всё ещё читается при
повреждении» выпущена автономным продюсером **трижды**:

| дата | slug | заголовок |
|---|---|---|
| 20.08.2026 | `auto-20260820-193301` | «Почему QR-код читается даже с оторванным углом» |
| 30.08.2026 | `auto-20260830-082101` | «Почему QR-код читается, даже если часть закрыта?» |
| 31.08.2026 | `auto-20260831-150301` | «Почему QR-код не боится царапин?» |

Все три — один и тот же факт (избыточность кодов Рида-Соломона в QR:
код специально хранит больше данных, чем нужно, поэтому переживает
потерю/порчу части модулей), поданный через три разных бытовых входа
(оторванный угол / закрытая часть / царапины). Пользователь дословно:
«Тема этого ролика уже третий раз повторяется... третий раз уже перебор.
Почему у нас сломалась дедупликация тем?»

### Как нашли

Пользователь указал на повтор по памяти (он смотрит все ролики). Проверка:
`grep -ril "qr" episodes/*.json` → 3 эпизода; сверка заголовков из
`episodes/<slug>.metadata.json` подтвердила один и тот же факт под тремя
разными формулировками.

### Почему сломалось (root cause)

Дедупликация тем **никогда не была детерминированным механизмом** — только
инструкция агенту внутри `tools/producer_scheduler.py::build_prompt`
(до правки, дословно): «Посмотри, что уже сделано (ls episodes/ и
episodes/drafts/) и НЕ повторяй последние эпизоды — ни конкретную тему,
ни (два ролика подряд) один и тот же хайповый кластер.»

Три независимых дыры в этой формулировке, все три сыграли одновременно:

1. **Область действия — только «последние»/«подряд».** QR-код повторился
   с разрывом в 10 дней (20.08 → 30.08) и ещё раз через сутки (30.08 →
   31.08). Формально ни одна пара не «подряд», проверка их не покрывала.
2. **`ls episodes/` не даёт темы.** Имена файлов — голые таймстампы
   (`auto-20260820-193301.json`), тема нигде не видна на уровне имени. Чтобы
   реально узнать содержание, агенту пришлось бы открыть все (на момент
   инцидента — 76) файлов эпизодов и прочитать заголовок в каждом — дорого,
   ничем не форсируется и, судя по результату, реально не делалось
   тщательно ни разу из трёх запусков.
3. **Даже при сравнении текстом — заголовки не совпадали текстуально.**
   «оторванным углом» / «часть закрыта» / «не боится царапин» — три разных
   фразы. Проверка была бы обязана сравнивать по СУТИ факта/механизма, а не
   по тексту, но инструкция этого не требовала явно.

Ни один из трёх запусков (Codex-оркестратор, каждый раз новый прогон без
памяти о предыдущих) не имел реального способа узнать, что тема уже
покрыта — только слабую, легко необязательную к исполнению подсказку.

### Что исправили в ролике

Не применимо — баг не в конкретном ролике, а в выборе темы для будущих
запусков. Три существующих QR-эпизода остаются как есть (не будем
удалять/переделывать retroactively — контент сам по себе корректен, просто
избыточен).

### Что исправили в конвейере

`tools/producer_scheduler.py`:
- Новая функция `collect_past_episode_titles(root)` — детерминированно (без
  LLM, без агента) собирает YouTube-заголовки **всех**
  `episodes/*.metadata.json` (на момент правки — 53 файла с валидной
  metadata из 76 эпизодов; разница — эпизоды без прошедшего publish-этапа,
  ожидаемо). Один битый/неполный `metadata.json` пропускается
  (`except (OSError, ValueError, KeyError, TypeError)`), не валит сборку
  промпта целиком — список это подсказка для дедупликации, не
  критичный для корректности вход.
- `build_prompt()` теперь всегда вставляет готовый список прямо в текст
  промпта (не просит агента «сходить посмотреть») и явно требует сравнивать
  новую тему **по сути факта/механизма**, а не по тексту заголовка, приводя
  саму QR-триаду как прецедент прямо в тексте промпта.
- Старая формулировка «не повторяй последние (два подряд)» оставлена как
  есть (не противоречит новой), но теперь дополнена обязательной сверкой
  со всем списком, а не только соседними прогонами.

`tools/test_producer_scheduler.py` — этот файл был написан ранее (несла
32 теста), но **никогда не был закоммичен** (`git log` для него был
пуст) — исправлено попутно, взят под git. Добавлено 5 новых тестов:
- `PastTitlesTests` (3 теста): пустая директория → `[]`; отсутствующая
  `episodes/` → `[]`; сортировка по имени файла + пропуск битого JSON и
  файла без заголовка, с фикстурой на реальных трёх QR-заголовках.
- `PromptTests` (2 новых): `build_prompt` реально встраивает полный список
  заголовков и текст «ПО СУТИ факта/механизма» (изолированный temp-root,
  без зависимости от текущего состояния `episodes/` в репозитории); при
  пустой истории — корректный текст «первый запуск» вместо пустого блока.

Все 37 тестов (32 старых + 5 новых) зелёные:
`python3 -m pytest tools/test_producer_scheduler.py -q` → `37 passed, 4 subtests passed`.

### Урок / класс ошибки

- **Класс — «проверка есть в промпте, но не в коде»**: любая инструкция вида
  «посмотри Х и не повторяй Y», адресованная автономному LLM-агенту без
  памяти между запусками, не масштабируется — агент либо не станет
  вычитывать десятки файлов ради контекста, которого сам не просил, либо
  сравнит по поверхностному тексту, а не по факту. Если проверка важна —
  собирать вход детерминированно в Python и подавать готовым, а не
  надеяться, что агент «сходит и посмотрит» сам.
- **«Последние N» — не то же самое, что «все».** Формулировки вида
  «не повторяй последние два подряд» defatto ограничивают горизонт
  дедупликации искусственно коротким окном; при кадансе несколько роликов
  в день это окно исчерпывается за пределами одного дня.
- Дублирующиеся факты под разными заголовками сложнее ловить, чем
  дублирующиеся заголовки буквально — при следующих похожих доработках
  (например, если понадобится более строгая, программная проверка вместо
  промпт-инструкции) учитывать, что сравнение обязано быть семантическим,
  не строковым.
